# Component registry

`apps/obsidian-capture/src/component-registry.ts` defines the specimens used by both the Atlas view and snapshot capture. Each definition has a stable `id`, `name`, `category`, `source`, `implementation`, an array of variants, and a `render` factory. The factory instantiates a real Obsidian component and returns its DOM root plus a function that reads its current state.

To add a component, add one definition to `componentRegistry`. Use an API-backed factory when `source` is `public-api`. Give each variant a stable `id`, a visible `name`, and an expected `state`. The view automatically groups it by category and renders every variant; export captures those same rendered roots. Do not add a second capture-specific implementation.

To add a variant, add one item to that component's `variants` array and handle its `id` in the factory with public API methods. For example, `ButtonComponent` uses `setDisabled(true)` for `disabled` and `setCta()` for `cta`. Its `normal` and `cta` variants both have state `enabled`. `SearchComponent`, `TextComponent`, and `TextAreaComponent` use `setValue()` for `empty` and `filled`; text and textarea also use `setDisabled(true)`. `ToggleComponent` uses `setValue()` for `off` and `on`. `DropdownComponent` uses two fixed options; `default` selects the first, `selected` the second, and `disabled` keeps the first selected. `SliderComponent` uses `setLimits(0, 100, 1)` with 0, 50, and 100 as minimum, middle, and maximum; its disabled specimen stays at 50.

Export rebuilds specimens immediately before capture, so manual interaction with the examples does not silently change a named variant. Capture checks that each resulting state matches the variant definition. The exported `(id, variant)` pair identifies a specimen; `id` remains the stable component type ID.

Batch 2 adds `ColorComponent` (`violet`, `red`, `disabled`), `ExtraButtonComponent` (`normal`, `disabled`), `MomentFormatComponent` (`empty`, `filled`, `disabled`), and `ProgressBarComponent` (`empty`, `half`, `complete`). Colors use fixed hex values, the icon button uses Obsidian's built-in `settings` icon, the format input uses `YYYY-MM-DD`, and progress uses 0/50/100 through `setValue()`.

Runtime DOM details: Color renders an `input[type=color]`; the disabled state is exposed by its input property. ExtraButton renders a `div` with an SVG child; `setDisabled(true)` adds `is-disabled` to that root. The Atlas uses a flex host so this icon button keeps its natural width. MomentFormat inherits TextComponent's input DOM. Its optional `sampleEl` is deliberately not attached here, avoiding a sample that may depend on the current date and locale; this specimen captures the format input only. ProgressBar renders a `setting-progress-bar` root with a nested `setting-progress-bar-inner`; the inner width reflects the percentage. Root widths for flex/grid content remain dependent on the Atlas viewport.

Batch 3 adds `Setting` (`standard`, `heading`, `disabled`, `error`), `SettingGroup` (`standard`, `with-search`), `DisplayValueComponent` (`value`, `warning`, `empty`), and `SecretComponent` (`unselected`). `render` now receives the current public `App` as its third argument for APIs such as `SecretComponent`. Settings specimens use the real `Setting` row as their DOM root. `SettingGroup` uses its generated group root. `DisplayValueComponent` is created through `Setting.addDisplayValue` because the direct constructor is absent from the observed runtime export despite appearing in the SDK types. `SecretComponent` is created through `Setting.addComponent` with an empty selection, without writing to `SecretStorage`. See [runtime observations](settings-batch.md).

`triggeredSurfaces` is an optional registry note for UI opened outside a specimen's captured root. It currently records `SecretComponent` → `obsidian.secret-setup-dialog` through **Link…**. It does not add a component, variant, rendered specimen, or export field. See the [surface inspection](triggered-surfaces.md) before extending the snapshot schema for overlays.

Batch 4 adds direct overlays: `Modal`, `ConfirmationModal`, `Menu`, and `Notice`. Their factories return `activate`, `getCaptureRoot`, and `deactivate` as well as the normal state reader. The view exposes an **Open specimen** button for each. Export opens and closes these surfaces one at a time, and `getCaptureRoot` selects the actual overlay DOM instead of the trigger host. See [batch 4 observations](overlays-batch.md).

Batch 5 adds `PopoverSuggest`, `AbstractInputSuggest`, `SuggestModal`, and `FuzzySuggestModal`. Their minimal subclasses implement the SDK's abstract hooks in `suggestion-fixtures.ts`; the registry still defines each `(id, variant)` and provides the same activation/capture/cleanup interface. The base `PopoverSuggest` exports only its empty shell. See [batch 5 observations](suggestions-batch.md).

Batch 6 adds `setTooltip/registered`, `displayTooltip/visible`, and `setIcon/settings` in the `Contextual` category. `setTooltip` captures the registered target only; `displayTooltip` captures the actual separate tooltip surface. `HoverPopover` was investigated but not added because the installed SDK has no public close method. See [batch 6 observations](contextual-batch.md).
